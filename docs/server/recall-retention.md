# Bounded Recall retention and retryable blob cleanup

The configured retention task now runs Recall retention through a process-local coordinator. It drops a batch of at most four valid, named old day partitions of the resolved `screen_frames` parent, with schema-qualified identifiers. Invalid calendar names do not consume that batch. Partition-name validation uses PostgreSQL 16 `pg_input_is_valid`, matching the repository’s PostgreSQL 16 deployment requirement. Each batch is transactional; committed drops invalidate the existing partition cache. The catalog DEFAULT child is excluded from day-partition drops even if its name resembles an old day partition. Other nonstandard day partitions are not dropped by this stage.

Each pass also attempts **one transactional batch of at most 256 expired DEFAULT rows**, before blob scanning. It resolves `screen_frames` using the connection's search path, locks that schema-qualified parent in SHARE UPDATE EXCLUSIVE mode, validates a single-column RANGE key on `captured_at` (TIMESTAMPTZ or DATE), and resolves the actual DEFAULT leaf through `pg_partitioned_table.partdefid` and `pg_inherits`. It locks and revalidates the child's catalog identity before deleting from `ONLY` that qualified relation. Names, including nonstandard/quoted names, are not evidence of DEFAULT membership. No DEFAULT child is a successful zero-row transaction. Plain parents, expression/multi-column/other partition keys and subpartitioned DEFAULT children fail explicitly without row deletion.

The predicate is `captured_at < midnight UTC on the configured cutoff day`; equality and more recent rows survive regardless of their blob path. Selected rows are ordered by timestamp and physical tuple location, limited, and locked with `FOR UPDATE SKIP LOCKED`. Inserts remain possible during pruning. Locked rows wait for later passes without blocking other available expired rows; a finite unlocked backlog makes progress across passes. Continuous earlier expired inserts or persistently locked rows can delay others. No fairness or immediate drain guarantee is claimed under arbitrary external writers. Tuple locations are used only in the same transaction and leaf. A statement/lock error rolls back the entire row batch. Local statement/lock limits are two/one seconds, with a five-second outer deadline capped by the coordinator's run deadline.

`default_batches_attempted` and `default_batches_committed` are zero or one per pass. `default_rows_deleted` counts only a batch whose commit was acknowledged; `default_prune_failures` counts failed/timed-out attempts. `default_rows_pending` is `Some(true/false)` only after an acknowledged commit and reflects an EXISTS check for expired rows (including rows skipped because locked); `None` means failed/unattempted, not zero remaining rows. The pending check observes its own statement snapshot, not future uploads, and is not a remaining-row count. An outer timeout during commit can have an uncertain database outcome; no acknowledged deletion count is reported in that case. Indexed paths still require the independent all-partition database absence check under the device gate before removal.

Ingestion continues accepting late expired captures under its existing permissions. A late upload committed after the row batch protects its directory during that pass and can be pruned on a later pass. This slice adds no ingestion-age rejection or permission-policy changes. DEFAULT row pruning and day-directory eligibility both use the configured UTC day cutoff. Rows with current timestamps pointing to old directories continue protecting those paths.

Directory cleanup is independent of which partitions were dropped in that pass, so a failed cleanup after a successful DROP can retry later. A retained directory cursor scans at most 512 entries and collects at most 32 old-day candidates per pass. The cursor continues across passes rather than restarting at the first device. Once enumeration completes, a later pass starts a new cycle and can retry previously failed or skipped candidates. Directories created behind a retained cursor likewise wait for a later cycle. A large tree may require many retention intervals to drain; this is not an immediate full reconciliation.

Only canonical lowercase UUID device directories and valid `YYYYMMDD` directories strictly older than the cutoff qualify. Configured-root ancestors, root, device and day are checked without following static symlinks, both while scanning and before removal. Parent traversal, symlinks and non-directory structures fail closed. The selected device's existing lifecycle gate is held exclusively from the database reference check through directory removal. Cooperating ingestion, blob reads, thumbnails, device deletion and registration use the same gate. An existing reference with the candidate's exact UUID/day prefix protects that directory, across all partitions (including default), captured dates and row owners. This deliberately protects an existing malformed cross-device row instead of deleting its actual path. There is no unconditional age-only deletion.

An accepted retention job owns its locks independently of its awaiting caller. Caller cancellation does not cancel the critical section. Non-abortable blocking filesystem workers independently retain both the coordinator lock and device gate until they actually exit. Overlapping runs report `skipped_running`. Gate acquisition waits at most two seconds; database calls have five-second outer deadlines plus transaction-local statement limits (two seconds, and one-second lock limits for partition/narrative work). Partition work has a 12-second outer deadline. A pass normally yields within its 30-second run budget, with five-second filesystem wait limits. A slow kernel/filesystem operation can continue beyond those limits while retaining its locks; no physical cancellation guarantee is claimed.

Logs distinguish a **bounded pass** from complete enumeration: `scan_complete` says only that the retained enumeration cursor reached its end, not that every directory was removed. `partition_batch_full` indicates that additional partition work may remain. `budget_exhausted` reports candidates left when the run deadline was reached. Gate, database, filesystem and narrative failures produce an error and an incomplete-pass report rather than success. Safe indexed directories are reported as protected. Failures are retried by later scan cycles; there is no durable retry queue, so a server restart resets the cursor to the beginning.

Reference checks use a conservative all-owner `blob_ref LIKE 'UUID/YYYYMMDD/%'` query. There is currently no prefix index or filesystem-byte accounting, so each check can scan retained partitions. The fixed candidate count and query timeouts bound a pass but may limit cleanup throughput on large databases. This stage does not reclaim a specific unreferenced file inside an otherwise indexed day or assert capture coverage.

The coordinator and gates operate within one server process. Multiple server processes sharing a database/blob root need a distributed exclusion design. Static path validation is not an atomic filesystem sandbox against concurrent local-administrator replacement of ancestors or entries. Raw external database writers are outside the cooperating lifecycle protocol. These limits do not weaken protection for normal app ingestion and device operations within one process.

Verification uses session-private temporary PostgreSQL relations, dedicated random schemas for cross-session fixtures in a fresh disposable PostgreSQL container, and random disposable filesystem roots only. It covers committed partition-drop/failed-removal retry, default and cross-owner references, invalid partition names, bounded partition batches and parent scoping, static symlink refusal, scan progress across large devices, overlapping jobs, and lock lifetime after caller cancellation. No existing application database or blob tree was scanned or deleted.

Checks on this stage: full server suite passed 170 tests (123 regular, 44 temporary-PostgreSQL and three cross-session random-schema tests), including 20 retention tests (five filesystem/concurrency, 12 temporary-PostgreSQL and three cross-session cases). `cargo check --all-targets`, strict all-target Clippy (`-D warnings`), formatting and server diff whitespace checks passed. Both `TEST_DATABASE_URL` and `RECALL_TEST_DATABASE_URL` pointed to the newly created `postgres:16-alpine` container `vantyr-retention-concurrency-20261004`, bound only to `127.0.0.1:32770`. The fixture schemas were dropped (zero remaining fixture schemas verified), and that container was subsequently stopped and removed. The cross-session fixtures require the additional explicit opt-in `RECALL_RETENTION_DISPOSABLE_SCHEMA_TESTS=1` and matching `TEST_DATABASE_URL` / `RECALL_TEST_DATABASE_URL`; use them only with a fresh disposable database. They create and drop dedicated random schemas, with separate worker and observer connections whose search paths contain only the fixture schema. They verify real SKIP LOCKED behavior (including zero deletions with expired locked rows still pending), progress after releasing the row lock, retention of current rows, concurrent current ingestion, parent DETACH / child RENAME lock timeouts during the actual helper, and transaction rollback / relation-lock release after helper cancellation. A fixture-only trigger pauses deletion within the real two-second statement budget; production code has no runtime test hooks. The cooperating-ingestion and caller-cancellation tests additionally exercise the process coordinator/device-gate boundary. DEFAULT tests cover UTC timestamp equality, >batch progress, catalog identity with quoted/nonstandard names and decoys, recent cross-owner path protection, unsupported structures, trigger rejection rollback, statement timeout rollback, and safe cleanup after acknowledged row pruning.
