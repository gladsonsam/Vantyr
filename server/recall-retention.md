# Bounded Recall retention and retryable blob cleanup

The configured retention task now runs Recall retention through a process-local coordinator. It drops a batch of at most four valid, named old day partitions of the resolved `screen_frames` parent, with schema-qualified identifiers. Invalid calendar names do not consume that batch. Partition-name validation uses PostgreSQL 16 `pg_input_is_valid`, matching the repository’s PostgreSQL 16 deployment requirement. Each batch is transactional; committed drops invalidate the existing partition cache. Default-partition rows and partitions with nonstandard names are not pruned by this stage.

Directory cleanup is independent of which partitions were dropped in that pass, so a failed cleanup after a successful DROP can retry later. A retained directory cursor scans at most 512 entries and collects at most 32 old-day candidates per pass. The cursor continues across passes rather than restarting at the first device. Once enumeration completes, a later pass starts a new cycle and can retry previously failed or skipped candidates. Directories created behind a retained cursor likewise wait for a later cycle. A large tree may require many retention intervals to drain; this is not an immediate full reconciliation.

Only canonical lowercase UUID device directories and valid `YYYYMMDD` directories strictly older than the cutoff qualify. Configured-root ancestors, root, device and day are checked without following static symlinks, both while scanning and before removal. Parent traversal, symlinks and non-directory structures fail closed. The selected device's existing lifecycle gate is held exclusively from the database reference check through directory removal. Cooperating ingestion, blob reads, thumbnails, device deletion and registration use the same gate. An existing reference with the candidate's exact UUID/day prefix protects that directory, across all partitions (including default), captured dates and row owners. This deliberately protects an existing malformed cross-device row instead of deleting its actual path. There is no unconditional age-only deletion.

An accepted retention job owns its locks independently of its awaiting caller. Caller cancellation does not cancel the critical section. Non-abortable blocking filesystem workers independently retain both the coordinator lock and device gate until they actually exit. Overlapping runs report `skipped_running`. Gate acquisition waits at most two seconds; database calls have five-second outer deadlines plus transaction-local statement limits (two seconds, and one-second lock limits for partition/narrative work). Partition work has a 12-second outer deadline. A pass normally yields within its 30-second run budget, with five-second filesystem wait limits. A slow kernel/filesystem operation can continue beyond those limits while retaining its locks; no physical cancellation guarantee is claimed.

Logs distinguish a **bounded pass** from complete enumeration: `scan_complete` says only that the retained enumeration cursor reached its end, not that every directory was removed. `partition_batch_full` indicates that additional partition work may remain. `budget_exhausted` reports candidates left when the run deadline was reached. Gate, database, filesystem and narrative failures produce an error and an incomplete-pass report rather than success. Safe indexed directories are reported as protected. Failures are retried by later scan cycles; there is no durable retry queue, so a server restart resets the cursor to the beginning.

Reference checks use a conservative all-owner `blob_ref LIKE 'UUID/YYYYMMDD/%'` query. There is currently no prefix index or filesystem-byte accounting, so each check can scan retained partitions. The fixed candidate count and query timeouts bound a pass but may limit cleanup throughput on large databases. This stage does not prune old rows from the default partition, reclaim a specific unreferenced file inside an otherwise indexed day, or assert capture coverage.

The coordinator and gates operate within one server process. Multiple server processes sharing a database/blob root need a distributed exclusion design. Static path validation is not an atomic filesystem sandbox against concurrent local-administrator replacement of ancestors or entries. Raw external database writers are outside the cooperating lifecycle protocol. These limits do not weaken protection for normal app ingestion and device operations within one process.

Verification uses temporary PostgreSQL relations and random disposable filesystem roots only. It covers committed partition-drop/failed-removal retry, default and cross-owner references, invalid partition names, bounded partition batches and parent scoping, static symlink refusal, scan progress across large devices, overlapping jobs, and lock lifetime after caller cancellation. No existing application database or blob tree was scanned or deleted.

Checks on this stage: 11 focused retention tests (five filesystem/concurrency, six temporary-PostgreSQL cases); full server suite 161 passing tests (123 regular plus 38 temporary-PostgreSQL tests); strict all-target Clippy, formatting and whitespace checks passed. PostgreSQL tests ran against a newly created disposable `postgres:16-alpine` container bound only to a random localhost port, subsequently removed.
